# Release Notes

## v1.52.0 — 2026-08-02

### New Features

- **Version reporting on both halves of the sync system, and a cheap `GET /count` on the hub.** Neither half could previously answer "which build is this?" over the wire. The package had a version (`remind-me-mcp --version`), but only on the machine's own command line — useless for the actual question, which is asked *about a remote node* mid-incident. The hub had no version at all: the only way to tell which code a deployed container was running was to inspect the image. Both now report themselves, and the hub gained the polling-shaped counts endpoint that `/stats` was being (mis)used for.
- **`HUB_VERSION` (`hub/main.py`), reported by `/health`, `/count` and `/stats`.** A hand-bumped literal, deliberately: the Containerfile copies `main.py` and nothing else — no `pyproject.toml`, no git checkout — so anything computed at import time resolves to nothing inside the image. Versioned *independently* of the `remind-me-mcp` package rather than tracking it: the two are separate deployables on separate cadences (the package bumps on every client release; the hub is one file that changes a handful of times a year), so tying them together would make the hub's reported version churn on releases that never touched hub code — precisely the noise that would make it untrustworthy for the one question it answers. Bump rule documented in the constant's own docstring and `hub/README.md`: MAJOR for a wire-protocol break, MINOR for a new endpoint or response field, PATCH for a fix nothing can key off.
- **The hub's version is public (`/health`), its counts are not (`/count`, `/stats`).** A deliberate split, not an inconsistency. Verifying that a deploy actually rolled over is exactly the kind of check an operator does with a bare `curl`, and gating it behind the bearer token pushes `SYNC_SECRET` into shell history to answer a question that reveals nothing about content. The tradeoff taken is fingerprinting — which is why it stays a bare version string, with no commit, dependency set, or platform detail attached (locked by a test). Counts are the opposite case: totals leak how much an operator has stored and how fast it grows, so `/count` is bearer-gated exactly as `/stats` already was, and `/health` stays free of aggregates so it remains cheap and survives a Postgres outage.
- **`GET /count` is the cheap counterpart to `/stats`, not a duplicate of it.** `/stats` answers "how does my node differ from the hub, and *where*", and pays for it with two `GROUP BY` passes over the whole `memories` table plus `MIN`/`MAX` — the right cost once per reconcile, and the wrong cost for what operators actually reach for most often ("is the number going up?": a dashboard tile, a cron drift alarm, a check right after a bulk import). Before this, that question had no answer short of the full aggregate. `/count` never groups, and `?table=memories|entities|memory_entities|entity_relations` narrows it to a single `COUNT` so a poller doesn't scan tables it isn't watching. The cheapness is the feature, so a test fails the build if a `GROUP BY` ever appears in it.
- **`memories.live` is split out from `total`, on the same scan.** A node's user-visible count filters `deleted_at IS NULL` while the hub retains tombstones until `/admin/compact_tombstones` runs, so a single bare total compared across the two reads as permanent drift that isn't there. The split rides along on the same `COUNT(*) FILTER` pass and costs nothing extra.
- **The `table=` filter is allowlisted, because the name reaches the SQL as text.** `COUNT(*) FROM %s` is not a parameterizable position in Postgres, so the table name is interpolated — safe only because the value is checked against a fixed `_COUNTABLE` tuple first (an unknown value is a `400`, never a query). A test asserts the allowlist is still consulted, since dropping that check silently turns `?table=` into SQL injection.
- **Package version moved to a new leaf module, `remind_me_mcp/version.py`.** Not cosmetic: `__init__` imports `tools`/`server`, which reach `api`/`sync`/`peer_server`, so a module-level `from remind_me_mcp import __version__` in any of those reads the name off a half-initialized package and raises at import time — the server fails to *start*, on the machine that just upgraded. (This is why `updater.py` has always done that import inside functions.) A leaf module has no such cycle. `__init__` re-exports the name, so every existing caller is unchanged, and a test walks the package's top-level imports to fail the build if the trap is ever reintroduced.
- **Reported on the node side by `/health` (dashboard, unauthenticated — same posture as the hub's), `/health` (peer server, *behind* the sync secret, since that port binds all interfaces by default), `remind_me_sync_status`, and `remind_me_sync_reconcile`.** Reconcile reports both sides at once (`version` and `hub_version`) because it is already the place the two sides are compared — otherwise confirming a version skew means curl'ing the hub and matching it against a node by hand. `hub_version` is present-but-`null` against a hub predating this release, so "old hub" reads as a fact about the hub rather than a field the node failed to populate.
- **Testing follows the hub's existing constraint.** The hub ships as its own container with its own dependencies (`fastapi`, `psycopg`), neither of which is in this package's requirements, so no CI leg can import `hub/main.py` at all — new `tests/test_hub_version.py` and `tests/test_hub_count.py` are AST-based static checks in the established `tests/test_hub_stats.py` style, asserting the properties most expensive to get wrong and least visible in review (auth posture, no `GROUP BY`, allowlist present, every route reporting the version). They parse the routes' *executable* source with docstrings stripped — these handlers document their own security tradeoffs in prose, so a naive substring check would happily pass on the explanation of a leak instead of the leak. Runtime coverage of the real responses lives in `hub/e2e_test.py`, which now also asserts `/count` and `/stats` cannot disagree about the same records — the failure a separate cheap query path invites.

## v1.51.0 — 2026-08-02

### New Features

- **Audio transcription import (FT-32, #192)** — a new `audio` import kind (`remind_me_mcp/audio_import.py`, registered exactly like `pdf_import.py`/`image_import.py`) transcribes `.mp3`/`.m4a`/`.wav`/`.ogg` files via [faster-whisper](https://github.com/SYSTRAN/faster-whisper) (a CTranslate2 re-implementation of OpenAI's Whisper) and chunks the result **per transcript segment** — Whisper's own sentence/phrase-level output unit — with each chunk's metadata carrying a `start`/`end` timestamp (seconds), mirroring how `pdf_import.py` uses the page number as chunk context. `kind=auto` routes all four extensions unconditionally, same as `pdf`/`image` — there's nothing to content-sniff.
- **Library choice, researched and verified against real audio in-sandbox, not assumed.** Tried in order: (1) an ONNX option (`onnx-asr`, which does run a Whisper model on `onnxruntime` — the same runtime this server already depends on for the embedder/reranker/OCR) was rejected first: it only accepts raw PCM WAV, with no built-in decoder for compressed containers at all, so three of the four required extensions would need a *second* new dependency just for decoding. (2) [`pywhispercpp`](https://github.com/absadiki/pywhispercpp) (Python bindings for whisper.cpp, lighter-weight than a full CTranslate2/PyTorch runtime) was tried next — it worked on a plain 16kHz WAV, but failed reproducibly on `.mp3`: it shells out to a **system** `ffmpeg` binary for anything else, hitting `Exception: FFMPEG is not installed or not in PATH.` in a sandbox with none installed — reintroducing exactly the class of dependency `pdf_import.py`/`image_import.py` already rejected once (pure-Python `pypdf` over poppler-utils; RapidOCR over pytesseract's system `tesseract` binary). (3) **`faster-whisper` (chosen)**: decodes every common audio container out of the box via its own bundled [PyAV](https://github.com/PyAV-Org/PyAV) (`av`) dependency, which ships a statically-linked ffmpeg build inside its own wheel — no system `ffmpeg` binary required — and already shares three of its four dependencies (`onnxruntime`, `huggingface-hub`, `tokenizers`) with this project's own `[semantic]` extra. `openai-whisper` (the heavier, plain-PyTorch reference implementation) was the documented last-resort fallback; not needed since faster-whisper worked cleanly.
- **Model size default, chosen deliberately smaller than Whisper's largest.** `config.AUDIO_MODEL_SIZE` (env `REMIND_ME_AUDIO_MODEL`) defaults to `base` (~145MB int8-quantized, ~74M parameters) rather than `large-v3` (~3GB) — trading some transcription accuracy for a small download and fast CPU-only inference, consistent with this being a local-first tool's DEFAULT, not its ceiling. Downloads from HuggingFace Hub on first use and caches under `MODEL_DIR`, exactly like the embedder/reranker's own ONNX models — the on-disk format differs (CTranslate2 conversion vs. ONNX) but the "download once, reuse forever" behavior is identical. Runs CPU-only, matching every other in-process model this server hosts.
- **Segment-based chunking is not optional here, unlike the issue's stated one-chunk fallback.** faster-whisper's `transcribe()` always returns timestamped segments — there is no "single transcript blob" mode to fall back to — so the one-chunk-per-file fallback the issue anticipated for a hypothetical non-segmenting backend was not implemented; it would be dead code against the library actually chosen. A segment too long for one memory is still split further by the shared `_chunk_text` (exactly like an oversized PDF page), with every sub-chunk keeping that segment's full timestamp range.
- New `tests/test_audio_import.py` (`pytest.importorskip("faster_whisper", ...)`-gated, matching the `[pdf]`/`[image]` extras' own skip convention): missing-dependency error path, `kind=auto` routing, hash dedup, and forced-kind validation all pass with real installed dependencies. Real audio is synthesized at test time with the `espeak-ng` command-line tool (itself gated on `shutil.which("espeak-ng")`, since it's a system tool outside the `audio` pip extra and not guaranteed present in every environment) and transcribed through the genuinely real library — but asserted on *shape* (non-empty text, sane monotonic timestamps), not exact wording: repeated direct testing during development showed CTranslate2's multi-threaded CPU inference is not bit-stable run-to-run on a synthesized, somewhat-robotic voice sitting close to the model's decision boundary (byte-identical input occasionally decoded to different words across runs, even with the language pinned) — a real, load-bearing finding about the chosen library's CPU behavior, not a hypothetical worry to hedge against. Tests needing exact, stable content (multi-segment chunking with precise timestamp pairs; the FTS5 search round-trip) mock `_get_whisper_model()`'s return value instead, isolating the connector's own fully-deterministic chunking/storage/search logic from ASR content variance.

## v1.50.0 — 2026-08-02

### New Features

- **Obsidian vault import (FT-31, #193)** — a new `obsidian` import kind (`remind_me_mcp/obsidian_import.py`, registered the same way `pdf`/`image`/`readwise` are) understands the Obsidian-flavored Markdown conventions the existing `document` kind treated as opaque prose: YAML frontmatter (`tags:` becomes memory tags, other fields land in `metadata.obsidian_frontmatter`), `[[Wikilink]]`/`[[Wikilink|Alias]]`/`[[Wikilink#Heading]]` references resolved into FT-04 knowledge-graph entities (create-or-match by note title, mention-linked to the memory), and inline `#tag` syntax (deduplicated against frontmatter tags). Chunking itself is unchanged — the connector strips frontmatter and hands the body to the existing per-section Markdown chunker (`importer._parse_document`) that `document` already uses.
- **Own connector kind, not a `document` enhancement.** Registered as `obsidian` (mirroring FT-19/FT-20's `pdf`/`image`/`readwise` precedent) rather than folded into `document`, so a plain (non-Obsidian) Markdown `document` import is completely unaffected, byte-for-byte. Two new, generically-named (not Obsidian-specific) reserved chunk-metadata keys — `extra_tags` and `mention_entities` — are handled centrally in `importer._ingest_parsed`, available to any future connector that needs the same tag/entity hook.
- **Zero-config vault detection, not a new env var.** `config.is_obsidian_vault()` treats a `.obsidian/` directory at or above a watched/imported path's root as the vault signal Obsidian itself already creates — an existing Obsidian user needs no new configuration. `config.resolve_import_kind()` upgrades `kind="auto"` to `"obsidian"` for a `.md`/`.markdown` file inside a detected vault; both `watcher.py` (live folder watching) and `import_directory` (one-shot bulk import) call it per file. `kind="auto"`'s *content* sniffing deliberately does NOT route to `obsidian` — frontmatter delimiters and double-bracket text both have legitimate non-Obsidian uses, so directory context is the reliable signal, content is not; a caller can still force `kind="obsidian"` explicitly for a note outside any detected vault.
- **`.obsidian/` config folder exclusion needed no code change.** Checked first, per the issue's own guidance: `FolderWatcher._candidate_files`'s existing hidden-directory skip (any path component starting with `.`) already excludes `.obsidian/` as just another dot-directory — confirmed, not assumed, by a new regression test.
- **Frontmatter parsing: hand-rolled, not a new `pyyaml` dependency.** `pyyaml` is not a direct, always-installed dependency of this project's base install — it only appears in the venv transitively through optional extras (`huggingface_hub` under `semantic`, `rapidocr-onnxruntime` under `image`). Consistent with this codebase's repeated minimal-dependency bias (`rate_limit.py`/`telemetry.py`/`metrics.py` all hand-roll small formats rather than add a library), a small parser covering the common flat `key: value` / `key: [list]` / `key:\n  - item` shapes real Obsidian frontmatter overwhelmingly uses was preferred over a new mandatory dependency for this bounded a need. It never crashes on what it can't represent: any unsupported YAML construct (nested mappings, flow mappings, anchors, block scalars) degrades the whole frontmatter block to "no fields extracted, body still stripped and imported cleanly" rather than raising.
- **Wikilink parsing reuses this codebase's own `[[...]]` implementation** (`wiki._WIKILINK_RE`, the FT-08 LLM Wiki layer's pattern) rather than a second bracket-matching regex, layering `#Heading`/`^block` anchor-stripping on top. **Documented v1 limitation**: the heading/block anchor is stripped, not resolved separately — `[[Note#Heading]]` resolves to the same `Note` entity a plain `[[Note]]` link would. **Gap noted in passing**: `wiki.py`'s own `parse_wikilinks` does not strip a `#Heading` suffix either — a wiki page's own `[[Page#Section]]` link forks a separate slug instead of resolving to `Page` — a pre-existing gap in the wiki layer itself, deliberately left unfixed here (out of scope, its own separate blast radius) since Obsidian import does its own anchor-stripping independently and is unaffected by it.
- New `tests/test_obsidian_import.py` (33 tests) covers frontmatter parsing (correct extraction, and three distinct malformed/complex shapes all degrading to body-only ingestion instead of crashing), wikilink resolution (plain and aliased links to the same title resolving to the same entity, a link to a not-yet-imported note title still creating/matching an entity, mentions attributed to the specific chunk that contains them), inline `#tag` extraction (basic, heading/code-fence/inline-code/wikilink-anchor exclusion, purely-numeric rejection, dedup against frontmatter tags), `.obsidian/` exclusion from a live watcher scan, vault detection (root, ancestor, import-roots-bounded, plain-directory negative), `kind="auto"` resolution both inside and outside a detected vault, and a full round-trip (import → `remind_me_search` finds it → `remind_me_entity` finds the wikilink-derived entity).

## v1.49.0 — 2026-08-02

### New Features

- **Free-text contradiction candidates (FT-30, #201)** — a new `remind_me_contradiction_candidates` tool (`limit`, default 20) surfaces bounded PAIRS of memories that might conflict but were never caught by the EXISTING structured-triple supersession mechanism (`db._supersede_contradicting_facts`: a new/updated SPO triple sharing an existing memory's subject+predicate but a different object auto-supersedes it — see the README's "Contradiction-based supersession" section). That mechanism only fires on exact triple structure; it says nothing about two pieces of free-text prose that conflict without ever sharing a formal subject/predicate ("I moved to Boston last month" vs. "My apartment in Seattle has great light" as two unstructured memories). This tool is the free-text analog, conceptually the prose sibling of `remind_me_recalibrate_candidates` (#200): a deterministic heuristic surfaces candidates, the calling Claude session does the actual judgment.
- **Architectural correction from the issue's literal text, the same one #200 made first.** The issue proposed "a periodic (scheduler-loop-hosted) LLM pass." This server has no in-server LLM dependency and never calls an LLM API itself — a Python background thread has no LLM to call, only deterministic code to run. Built as the same two-phase, Claude-driven pattern as #200: the tool surfaces structured candidate PAIRS via a deterministic heuristic, the calling session judges whether a pair genuinely conflicts, and — deliberately — there is no third "apply"/"resolve" tool. There is no scheduler wiring anywhere in this change.
- **The candidate-pairing heuristic (`remind_me_mcp/maintenance.py`, `CONTRADICTION_CANDIDATE_PAIRS_SQL`), bounded two ways instead of all-pairs.** All-pairs comparison across a vault is O(n²) and mostly wasted work, so a pair is only surfaced when: (1) both memories share at least one linked entity in the entity graph (FT-04, `memory_entities` — the same graph `remind_me_entity` traverses), since two memories mentioning nothing in common are extremely unlikely to be a direct contradiction; and (2) the pair isn't already resolvable by the exact-triple mechanism (a normalized subject+predicate match is excluded) — which the new tests show is close to structurally unobservable anyway, since the write path already supersedes one side the moment a second matching-triple memory is written, so both can never be simultaneously live to compare. Non-`dialog`, non-superseded, non-deleted memories only.
- **Deliberately no third "apply"/"resolve" tool**, mirroring #200's decision. Once the calling session confirms a genuine contradiction, it acts with the EXISTING `remind_me_update` (correct the stale memory in place), `remind_me_delete` (remove it), or `remind_me_add` with an explicit `subject`/`predicate`/`object` triple naming the corrected fact — the last of which also lets the exact-triple mechanism catch any future conflict on the same claim automatically. Building a redundant write path would just duplicate those.
- **Maintenance nudge integration.** A new `contradiction_candidates` queue joins `maintenance.py`'s `_QUEUES`/`_LABELS`/`_QUEUE_PROMPTS` tables alongside the five queues before it — `_QUEUES`' shape was generalized with an `is_full_query` flag since this queue counts JOINed pairs rather than a single-table `WHERE` clause (every existing queue's entry and behavior is unchanged; the flag is `False` for all of them), same `NUDGE_THRESHOLD`/`NUDGE_INTERVAL` throttle. A matching `review_contradictions` prompt was added to `tool_profiles.py`'s `MAINTENANCE`/`MAINTENANCE_PROMPTS` tiers alongside the tool.
- New `tests/test_contradictions.py` covers the pairing heuristic (a shared entity makes a candidate pair; no shared entity doesn't; a normalized subject+predicate match is excluded, both by construction — since it can't coexist live — and directly, by the exclusion clause itself; a differently-worded predicate for the same subject is NOT excluded, matching the exact-triple mechanism's own documented narrowness; `dialog`/superseded/deleted memories are excluded; a memory is never paired with itself; multiple shared entities still yield one pair, not a duplicate), the tool's bounded output and read-only behavior (asserts the full `memories` table is byte-identical before/after a call), the nudge integration at threshold, and — the architectural correction's own regression guard — that `tools/contradictions.py` imports nothing from `scheduler.py`.

## v1.48.0 — 2026-08-02

### New Features

- **Importance recalibration candidates (FT-29, #200)** — a new `remind_me_recalibrate_candidates` tool (`limit`, default 20) surfaces old, high-importance memories that have never received a `remind_me_feedback` signal, for review: nothing previously re-evaluated whether a memory's *original* importance classification had gone stale (the issue's own examples: a "decision" later reversed by a different memory, or a "fact" superseded in spirit but not via the formal triple-supersession mechanism).
- **Architectural correction from the issue's literal text, made deliberately.** The issue proposed "a periodic (scheduler-loop-hosted) LLM-driven pass," following the pattern of the reminder/digest/analytics-snapshot scheduler loops (#186/#187/#188). This server has no in-server LLM dependency and never calls an LLM API itself (`tools/normalize.py`'s own docstring establishes this same posture for `remind_me_normalize_batch`) — a Python background thread has no LLM to call, only deterministic code to run. Built instead as the established two-phase, Claude-driven pattern: `remind_me_recalibrate_candidates` surfaces structured candidate data via a deterministic heuristic, the calling Claude session does the actual reasoning, and — deliberately — there is no third "apply" tool. The issue itself names the natural apply half: the EXISTING `remind_me_reclassify`/`remind_me_reclassify_batch` tools (a genuine `memory_type` change) or `remind_me_feedback` (a pure importance nudge via `base_weight`, no type change) — building a redundant write path would just duplicate reclassify's.
- **The candidate heuristic (`remind_me_mcp/maintenance.py`, `RECALIBRATION_CANDIDATE_WHERE`), deterministic and narrowing only.** A memory qualifies when it looks important — `base_weight >= 1.15` (matching `vitality.BASE_WEIGHT_TYPE_PRIORS`' fact/insight write-time seed, not an arbitrary cutoff) **or** its `memory_type` implies durability on its own (`decision`, `fact`, the issue's own two examples) — **and** has gone stale (no access/creation activity in the last `RECALIBRATION_STALE_DAYS` = 90 days) **and** has never received a `remind_me_feedback` signal, used as the closest available proxy for "never actually reviewed" since nothing else in the schema records that. Superseded and soft-deleted memories are excluded. The `NOT EXISTS` against `memory_feedback` is correlated but index-backed (`idx_memory_feedback_memory_id`), the same shape `UNANNOTATED_WHERE` already relies on — not the O(n·m) table-scan trap issue #120 fixed for `UNNORMALIZED_WHERE`'s different, non-indexed case.
- **Maintenance nudge integration, following the exact existing pattern.** A new `recalibration_candidates` queue joins `maintenance.py`'s `_QUEUES`/`_LABELS`/`_QUEUE_PROMPTS` tables exactly like the four queues before it, so `maybe_maintenance_notice`/`remind_me_server_status` can mention "N memories due for an importance review" the same way they already mention undecomposed captures, unannotated memories, unnormalized imports, and unclassified memories — same `NUDGE_THRESHOLD`/`NUDGE_INTERVAL` throttle, no new mechanism.
- **New prompt, `recalibrate_importance`** (`remind_me_recalibrate_candidates` → `remind_me_reclassify`/`remind_me_feedback`), added to `tool_profiles.py`'s `MAINTENANCE`/`MAINTENANCE_PROMPTS` tiers alongside the tool itself, so the `standard` profile keeps the loop usable and `core` hides both consistently with every other maintenance loop.
- New `tests/test_recalibrate.py` covers the heuristic (old+important+never-fed-back memories qualify; recently-accessed, already-fed-back, low-importance, superseded, and deleted memories don't; a durable `memory_type` qualifies even at the default `base_weight`, and vice versa; staleness falls back to `created_at` when a memory was never accessed), the tool's bounded/shaped output, the nudge integration at threshold, and — the architectural correction's own regression guard — that `tools/recalibrate.py` imports nothing from `scheduler.py`.

## v1.46.0 — 2026-08-02

### New Features

- **Optional cloud upload of backups (FT-27, #196)** — a new `remind_me_mcp/cloud_backup.py` module and four new env vars (`REMIND_ME_BACKUP_S3_BUCKET`, `REMIND_ME_BACKUP_S3_PREFIX`, `REMIND_ME_BACKUP_S3_ENDPOINT_URL`, `REMIND_ME_BACKUP_S3_REGION`) let `remind_me_backup`/the pre-migration snapshot also upload a copy of every backup to S3 or an S3-compatible bucket. `boto3` (the AWS SDK) was chosen deliberately as the one-client-covers-most-providers option — its S3 client talks to real AWS S3 and, via `endpoint_url`, essentially every S3-compatible provider too (Backblaze B2, a self-hosted MinIO, ...), so this needed no per-provider integration. Gated behind a new `cloud-backup` optional extra; the base install (and every other extras group) has zero new dependency.
- **A strict post-success hook, not a race with the local write.** `backup.create_backup`'s existing local-first discipline (write to a `.tmp` path, `os.replace` into the final name only on success — issue #149) is unchanged; the new upload call is inserted immediately after that rename completes, so `list_backups`/`_prune_old_backups` are never affected by cloud upload succeeding, failing, or being unconfigured. The uploaded object key reuses the same filename `create_backup` already generated locally (joined with the optional prefix), so a local backup and its cloud copy correspond 1:1 by name.
- **No new credential env var — boto3's own chain, deliberately.** Credentials are resolved entirely by `boto3`'s standard chain (`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` env vars, the shared `~/.aws/credentials` file, an EC2/ECS/Lambda instance role, ...) rather than a bespoke `REMIND_ME_BACKUP_S3_*` secret — reinventing a parallel credential-storage convention here would be worse, not better, than relying on the one `boto3` already hardens.
- **The plaintext-upload consent gate — the issue's central design ask.** Per ARCHITECTURE.md's "Encryption at rest" section (#184): when `REMIND_ME_DB_ENCRYPTION_KEY` is set, the local backup file is already SQLCipher ciphertext (confirmed by #184's own `test_encrypted_file_is_not_plaintext_readable` test), so uploading it as-is is safe by default and needs no extra flag. When the key is *not* set, the backup is plaintext personal data, and uploading it to a third-party bucket introduces a real, distinct risk — cloud upload is refused with a clear explanatory error unless the new `REMIND_ME_BACKUP_S3_ALLOW_PLAINTEXT_UPLOAD` opt-in is explicitly set. A silently-uploaded plaintext backup was treated as an unacceptable default, not an edge case worth skipping.
- **Failure discipline mirrors `notifications.py`'s "never raise out of the calling path" rule (#180).** A missing `boto3` (bucket configured but the `cloud-backup` extra not installed), the plaintext gate refusing, and any `boto3`/network failure during the upload itself are all logged at `error` level inside `upload_backup` and swallowed — never propagated into `create_backup`. The local backup remains this codebase's primary guarantee (issue #17/#149); cloud upload is strictly a best-effort enhancement layered on top of it.

### New Features

- **Saved and watched searches (FT-26, #194)** — four new tools, `remind_me_save_search`/`remind_me_list_saved_searches`/`remind_me_run_saved_search`/`remind_me_delete_saved_search` (new `tools/saved_searches.py`), let a `remind_me_search` query be named, re-run on demand, and — via `watch: bool = False` — polled in the background for new matches, with `notify()` (issue #180) firing when one shows up.
- **Storage: two new local-only tables (migration v26→v27)** — `saved_searches` (`name` UNIQUE, so `remind_me_save_search` upserts by name — saving again under an existing name updates it in place, the same convention `remind_me_wiki_write` already uses for pages) and `saved_search_seen_memories` (`saved_search_id`, `memory_id`, `first_seen_at`, unique-indexed on the pair). - **Storage-shape judgment call: a dedicated seen-memories table, not a single watermark.** The digest check's `sync_flags` single-timestamp watermark (`digest_last_sent_at`) doesn't fit here — watch-polling needs a per-(saved search, memory) fact ("have I already notified about *this specific* match"), which one row per search can't represent, so a dedicated table was the right call instead.

Only a match that appears on a **later** poll, absent from what was seeded, is treated as genuinely new and fires exactly one notification; a repeat poll of the same match never re-fires.
- **Watch-polling piggybacks on the existing scheduler loop**, on its own coarser cadence (`REMIND_ME_SAVED_SEARCH_POLL_INTERVAL`, default 300s vs. the reminder poll's 60s default) — a persisted-watermark due-check in `sync_flags`, mirroring `digest.is_digest_due`'s exact shape, rather than a second background thread. Unlike the digest interval, it isn't itself an opt-in switch: the due-check always runs, cheaply, and whether a pass does anything is gated per-search by `watch`. Bridges into the async search core via `asyncio.run` per watched search, since the scheduler thread is a plain thread, not an asyncio loop.
- **Core-extraction decision: reused `remind_me_search`'s existing core rather than re-extracting one.** The issue asked to check whether `remind_me_search` was already factored into a callable-without-FastMCP core (mirroring #188's `list_reminders`/`build_vitality_report` precedent) and, if not, extract one. It was checked: `tools.search.memory_search` — the function `@mcp.tool` decorates — is already a plain `async def` taking only its pydantic `MemorySearchInput`, with no FastMCP `Context`/dispatch dependency, proven directly callable by ~80 pre-existing `test_tools.py` call sites (`await memory_search(params)`). `remind_me_run_saved_search` and the watch-poller both call it directly, which guarantees byte-identical output to calling `remind_me_search` with equivalent params (including respecting `include_sensitive`'s default-off, issue #195, for free) rather than risking drift from a second ~400-line reimplementation of the hybrid-retrieval pipeline.
- **Cleanup on delete.** `remind_me_delete_saved_search` also removes the deleted search's `saved_search_seen_memories` rows — explicit hygiene rather than leaving them as orphaned dead weight keyed by an id nothing will query again, matching this codebase's general discipline around not leaving derived rows behind a delete (e.g. `memory_delete`'s chunk-vector cleanup, DI-01).
- New `tests/test_saved_searches.py` covers the migration, CRUD round-tripping (including update-by-name instead of duplication), that `remind_me_run_saved_search` reproduces exactly what `remind_me_search` itself returns for equivalent params, the full watch-polling lifecycle (first-poll seeding, a later genuinely-new match notifying exactly once and being recorded, no re-notification on repeat, `watch=false` searches never polled), the scheduler-loop wiring, and seen-row cleanup on delete.

## v1.40.0 — 2026-08-02

### New Features

- **Opt-in encryption at rest (FT-21, #184)** — setting `REMIND_ME_DB_ENCRYPTION_KEY` encrypts `memory.db` (and its backups) via [SQLCipher](https://www.zetetic.net/sqlcipher/), through the new `encryption` extra (`pip install remind-me-mcp[encryption]`, `sqlcipher3-wheels`). **Unset by default and fully unaffected** — verified by the complete pre-existing test suite passing unchanged with the flag untouched. See [ARCHITECTURE.md's "Encryption at rest" design note](ARCHITECTURE.md#encryption-at-rest-is-opt-in-not-default-issue-184) for the full rationale, coverage, and limitations; this entry summarizes scope.
- **Scope: what this version does and doesn't do.** A working, tested integration for the primary path — connection open, dict-style row access, `sqlite-vec` extension loading, and `Connection.backup()` all verified to function correctly end-to-end under encryption — not just config scaffolding. Two real, non-obvious compatibility gaps were found (via this feature's own tests, not speculation) and fixed at the sites this change directly touches: `sqlite3.Row`'s constructor requires an actual `sqlite3.Cursor` (raises `TypeError` against an sqlcipher3 cursor otherwise — fixed via a new `db._row_factory_class()`), and sqlcipher3 ships its own exception hierarchy disjoint from `sqlite3`'s, not a subclass (fixed at `_get_db()`'s vec-extension load and `backup.py`'s restore validation via a new `db._sqlite_driver_errors()` helper). **Explicitly not swept everywhere**: roughly 40 other `except sqlite3.OperationalError`/`IntegrityError`/`DatabaseError`-style handlers across `db.py` and `tools/*.py` (lock-retry logic, duplicate-content dedup, corruption detection) were not rewritten to also catch the sqlcipher3 equivalent — documented as a deliberate v1 gap in ARCHITECTURE.md, not an oversight, since auditing every one of those ~40 sites safely was judged out of scope for a first pass touching the storage layer every other feature in this series depends on.
- **v1 adoption story**: encryption must be enabled *before* an install's first run. There is no in-place re-encryption of an existing plaintext database in this version (SQLCipher's own `sqlcipher_export()` mechanism would be the way to add that later) — turning the key on against an existing plaintext `memory.db` fails to open it rather than silently doing the wrong thing. The same applies to backups: an encrypted backup needs the same key to restore; a plaintext backup can't be restored while a key is configured.
- **Environment-dependent by nature, not by omission**: `sqlcipher3-wheels` (chosen over the unmaintained `pysqlcipher3` and source-build-only `sqlcipher3`) ships a prebuilt `libsqlcipher`, so it installs cleanly with no system package dependency in the environment this was built and tested in — but like every other native optional dependency in this project (`sqlite-vec`, `onnxruntime`, `usearch`), it is not guaranteed to install everywhere, which is exactly why it's an extras group with a clear `RuntimeError` (not a silent fallback to plaintext) when the key is set but the package isn't installed.
- **Not implemented here (documented, not silently dropped)**: the hub's Postgres storage stays plaintext — encrypting it is an infrastructure-layer decision (disk encryption, Postgres TDE), documented in `hub/README.md`'s new "Security posture" section rather than built into this codebase. Decrypted-in-memory content and OS swap/hibernation files are also out of scope, same as any application-level encryption-at-rest feature.

## v1.33.0 — 2026-08-02

### Security

- **Rate limiting for `POST /ingest` and the remote MCP connector (#183)** — both HTTP surfaces this server can expose over a public tunnel now enforce a request-rate limit: `REMIND_ME_RATE_LIMIT_REQUESTS` (default 60) per `REMIND_ME_RATE_LIMIT_WINDOW_SECONDS` (default 60 seconds), returning `429` with a `Retry-After` header once exceeded. A new dependency-free `remind_me_mcp.rate_limit` module implements a fixed-window, in-memory `RateLimiter` guarded by a single `threading.Lock` — correct under both `webhook_server.py`'s threaded `BaseHTTPRequestHandler` and `remote.py`'s single-event-loop Starlette/ASGI app, so one implementation serves both without needing a second `asyncio.Lock`-based variant. No new pip dependency (no Redis) — matches this server's single-process, single-node design (ARCHITECTURE.md non-goals).
- **Ordering: rate limit runs before auth, keyed by IP with a dedicated bucket for the verified credential.** On both routes the limiter is the outermost check — an entirely unauthenticated flood is bounded (IP-keyed) before any auth work happens, closing off a class of anonymous-probe DoS a purely post-auth limiter would miss. A request presenting the exact `REMIND_ME_WEBHOOK_SECRET` / remote connector token (via the secret path or the legacy bearer header) gets its own dedicated, generous bucket instead of sharing the IP-keyed one — which matters specifically because both routes default to a loopback bind behind an HTTPS tunnel, where every remote caller's apparent IP is typically the tunnel's own forwarding address, indistinguishable between the legitimate owner and a random prober. `resolve_key()` deliberately never mints a bucket for a merely-*presented*, unverified credential (only an exact match earns the dedicated bucket) — otherwise an attacker could send a different random `Authorization` value on every request and dodge the limit entirely. In `remote.py`'s OAuth mode, dynamically-issued per-client access tokens aren't individually re-verified for this check (that would duplicate `SingleUserOAuthProvider.load_access_token`'s async, file-backed lookup purely for rate-limit bookkeeping); they share the IP-keyed bucket with anonymous traffic, a documented tradeoff.
- **Composes with existing auth, doesn't replace it.** The limiter is a separate, layered check (`webhook_server.WebhookHandler._rate_limited` / `remote.RateLimitMiddleware`) — a request that fails auth still gets its normal 401/404, unaffected by whether it also happened to be rate-limited. `REMIND_ME_RATE_LIMIT_ENABLED=""` disables enforcement on both routes entirely (new `config._env_bool` helper, mirroring how `REMIND_ME_RERANK=""` disables reranking). Issues #141 (webhook_server's missing exception guard) and #142 (no socket timeout on webhook_server.py/peer_server.py) are adjacent, already-filed gaps and are explicitly out of scope for this change.

## v1.28.0 — 2026-08-01

A production incident (a stuck query hanging the server, which masked a stuck sync cursor for over an hour) turned into a dozen tracked issues (#119-#130) covering the whole failure chain — not just the two live bugs, but the missing tests, tooling, and process guards that let them go unnoticed for so long.

### Fixed

- **`UNNORMALIZED_WHERE`'s correlated `NOT EXISTS` subquery pegged a CPU core for minutes on a real-size store** (~60K memories), making the server's single-threaded event loop unresponsive to every MCP call. Rewritten as a non-correlated `NOT IN` (SQLite materializes it once via `LIST SUBQUERY` + a bloom filter instead of re-scanning per row) plus a new expression index — 180s+ (never observed to finish) down to 0.01s. `UNANNOTATED_WHERE` was checked against the same failure shape and confirmed already fine (an existing unique index gives it a `SEARCH`, not a `SCAN`).
- **`remind_me_sync_reconcile` reported `pull-lag` (benign) for over an hour while a pull cursor was actually stuck.** It only checked `last_pull_age` (an attempt timestamp that updates even when nothing new arrives) — never whether the cursor's own content watermark had moved. A keyset cursor can't recover records that sit behind its own watermark (here: a historical gap from before a WSL→Windows node migration), so it kept "succeeding" every cycle while making zero progress. The verdict logic now tracks the watermark itself and reports `fault` once it's provably stalled across repeated attempts — extended to all four sync cursors (memory, entities, links, entity_relations), not just the primary one.
- **A large outbox backlog could starve pull for the entire time it took to drain.** `_push_outbox` looped until fully drained before `_pull_remote` ever ran, so one transient timeout deep into a big backlog could abort the cycle before pull got a turn — for as long as the backlog persisted. Push is now capped per cycle (`PUSH_BATCHES_PER_CYCLE`); pull always runs every cycle regardless of backlog size.
- **`check_for_update`/`_get_origin_url` could crash outright on Windows instead of degrading gracefully.** Both caught `FileNotFoundError` for "the git subprocess couldn't even start" (a missing/invalid repo path), but Windows raises `NotADirectoryError` for that case — a sibling of `FileNotFoundError` under `OSError`, not a subclass, so it went uncaught. Widened to `OSError`. Found via 11 pre-existing `test_updater.py` failures on this platform; two more in the same file were genuine test bugs (a POSIX-only `fcntl` test with no Windows equivalent to exercise, now skipped there by design, and a hardcoded `/`-separated path assertion that never matched Windows' native backslashes).

### New Features

- **`remind_me_sync_repair`** — resets a stuck sync cursor (any of the four) to force a full re-pull, through the server's own DB connection. Previously recovering from a stuck cursor meant hand-editing `sync_log` via a second raw SQLite connection to the live database file. Requires `confirm=True` (a full re-pull re-checks everything the remote has and can trigger background re-embedding — real cost, not risk).
- **A single-instance lock for `--serve-mcp`/combined mode.** Nothing previously stopped two server processes from running against the same DB concurrently — in this incident, an orphaned hung instance plus a fresh launch that failed to bind its port but kept running anyway, both holding open DB connections and background sync threads. Mirrors the PID-file pattern `--serve-ui` already used.
- **A slow-call watchdog** (`REMIND_ME_SLOW_CALL_SECONDS`, default 30). Arms `faulthandler.dump_traceback_later` around every tool call — a plain `asyncio` timer can't catch a thread stuck in synchronous CPU-bound code (a blocked event loop can't run its own watchdog), which is exactly the failure mode this incident hit. Diagnosing it live required manually installing and running `py-spy`; this dumps every thread's stack to stderr automatically once a call runs long. State (armed/threshold/calls-in-flight) is surfaced in `remind_me_server_status`.

### Process

- A perf-regression test (`EXPLAIN QUERY PLAN` shape, not a timing threshold — deterministic regardless of row count) now guards the two hot maintenance queries against reintroducing a correlated table scan.
- `start_server.ps1` (local, untracked) now refuses to spawn a second instance instead of silently leaving a bind-failed orphan running, and pins UTF-8 on its log redirect (it was previously inheriting whichever default a given launch path used, garbling roughly half the log).
- README now recommends a short per-server MCP client timeout (30-60s) — a genuinely stuck call sitting silent for a long default idle timeout is itself what made this incident's diagnosis slow to start.

## v1.27.0 — 2026-08-01

Reverses a call made in v1.26.0 on bad data. That release documented the tool-profile gate as "evaluated and not built," citing a ~7k-token saving as too small to justify. **That figure was wrong by 2.6x**: it counted only `description` strings and ignored input schemas, which are the larger half of what a client is actually billed for. The real surface is ~21k tokens, and core-only saves ~13.6k.

### New Features

- **`REMIND_ME_TOOL_PROFILE`** — `full` (default, 46 tools, ~21k), `standard` (30, ~14.8k — drops imports/sync/backup/updater/ops), `core` (17, ~7.8k — conversational only). Default `full` means upgrading never narrows an existing deployment. `standard` keeps the maintenance loops so a maintenance pass still works; `core` hides them *and* their prompts, since a prompt sequencing tools the client cannot see is worse than absent.
- **`remind_me_server_status` reports the surface cost and the active profile.** This is what makes the knob discoverable — nobody goes hunting for an env var to fix a cost they cannot see, which is the same lesson as the v1.25.0 nudges. `remind_me_server_status` is consequently pinned into `core`: a profile you cannot diagnose from inside a session is a trap.
- **Slimmed `remind_me_search`'s schema** — 1398 → 1136 tokens (~19%). It is simultaneously the hottest tool and the most expensive one, and *no profile can narrow it* because every session needs it, so it is the one place where a saving reaches every deployment regardless of configuration. The flag descriptions narrated response shape ("in a separate `related_via_entities` section", "does not affect the main ranking"); they now describe only the call decision — when to set the flag — and the response-shape detail lives in the README, where it already was.

### Design notes

- **What a profile does not fix.** It was originally proposed as a tool-selection-accuracy fix. It is not one, and the code says so: the tools that genuinely compete — `search`/`list`/`get`/`entity`, all reading as "find things" — are *every one of them in `core`*, so no profile can separate them. v1.26.0's disambiguation handles that. A test asserts the cluster survives every profile, so the distinction cannot quietly erode.
- **Hidden means gone.** Pruning removes entries from the FastMCP managers, so a hidden tool is unlistable *and* uncallable rather than merely undocumented — no listable/callable split to trip over.
- **Unknown tools default to the most restricted tier.** Membership is defined by `CORE`/`MAINTENANCE` allow-lists, so a newly added tool cannot smuggle itself into a narrowed surface by existing. A test also asserts every name in those sets is a real registered tool, since a typo would silently drop a working tool from `standard`.
- An unrecognised `REMIND_ME_TOOL_PROFILE` logs a warning and falls back to `full` — a typo must not silently hide half the surface.

- **Occasional feedback hint on search responses**, throttled on its own timer (`REMIND_ME_FEEDBACK_HINT_INTERVAL`, default 2h) and worded toward the query-contextual form.
- A search response now carries **at most one** advisory. A maintenance backlog is concrete work to do, so it outranks the standing feedback affordance; stacking both would train the reader to skip the tail of every search, which is what both signals exist to avoid.

### Design notes

- **Why the profile gate was dropped.** Measured, hiding every non-core tool saves ~7k of ~8.1k tokens of tool descriptions per session — a real number. But the tools that actually compete are `search`/`list`/`get`/`entity`, and *all four are in the core set a profile would keep*. Hiding admin tools cannot fix a confusion that lives entirely among the tools you keep. Disambiguation costs ~425 tokens, hides nothing, needs no restart to change, and adds no permanent config axis. Recorded in the README's "Design Scope" with the numbers, so the call is revisitable rather than folklore — and if context pressure alone ever becomes binding, a gate should ship default-`full` so nothing silently stops working.
- The nudge throttle generalised from one global timer to named timers, so the maintenance nudge and the feedback hint cannot silence each other by claiming the same slot.

## v1.22.0 — 2026-07-31

Fixes the four sync-observability defects recorded in v1.21.1 (**SY-15** … **SY-18**). Behaviour change and a schema migration (v19 → v20) — not a patch release.

### SY-18: split the sync cursor from the liveness clock

`sync_log` had one column pair doing two jobs: `last_pull`/`last_pull_id` is the keyset resume-cursor over a remote's record stream, and `last_push` was supposed to be a liveness heartbeat but was never written by any code path. The 1.21.1 proposal suggested renaming the cursor columns to `pull_cursor_ts`/`pull_cursor_id`; this codebase's migration history is strictly additive (every prior migration adds a column via a suppressed `ALTER`, never renames or drops — see `_migrate_v8_to_v9` through `_migrate_v19_to_v20`), so the cursor columns were left exactly as-is and three new wall-clock columns were added instead:

- **`last_attempt_at`** — touched before contacting a remote, success or failure. The load-bearing one: with only `last_error` (null in the healthy case), "never tried", "tried and failed silently", and "tried and it worked" were indistinguishable.
- **`last_push_at`** — touched when `_push_outbox` completes a cycle against a remote, empty batch or not.
- **`last_pull_at`** — touched when a pull cycle completes, independent of whether the content cursor advanced.

All three are written uniformly for hub and every peer, since `_push_outbox`/`_pull_remote`/`_pull_graph_table` are already parameterized on `remote_id` with no hub-specific branching.

### SY-15: `last_push` reads as "never pushed" — fixed

Direct consequence of SY-18: `_push_outbox` now writes `last_push_at`, so `get_sync_status`'s `remotes[]` entries report a real push time instead of the epoch default. `ever_contacted` is now keyed off `last_attempt_at` rather than a pull/push pair that could never both be populated.

### SY-17: quiet-but-healthy remote read as `fault` — fixed

`reconcile_with_hub`'s verdict now compares wall-clock `last_pull_at` against the grace window instead of the `last_pull` content cursor, so a remote that's contacted every cycle but has nothing new to send no longer looks like a dead pull.

### SY-16: outbox counters measured echo suppression, not push progress — fixed

`pending`/`sent`/`oldest_pending_at` (and the reconcile `outbox_pending`) previously read `sync_outbox.sent_at`, which is only ever set by echo suppression (a pulled-in record's own outbox trigger being cancelled) — never by a successful push. A node that mostly writes its own memories therefore reported `drain: stalled` permanently, regardless of whether pushes were landing. These now derive from `sync_sends` via a new `_pending_to_remote` helper, mirroring `_push_outbox`'s own row-selection exactly: a row stops counting once it's genuinely acked by that remote, or was itself an echo. Each `remotes[]` entry also reports its own per-remote `pending` count.

### Also

- `remotes[]` no longer lists the synthetic `{remote_id}#entities` / `#links` / `#entity_relations` graph-cursor rows `_pull_graph_table` stores internally — those aren't remotes.
- Schema migration `v19 → v20` (`_migrate_v19_to_v20`, `db.py`): additive only, no backfill (the contact history was never recorded, so there's nothing to backfill from).

## v1.21.1 — 2026-07-31

Documentation only — no behaviour change. Records four sync-observability defects (**SY-15** … **SY-18**) found while diagnosing an apparent hub outage that turned out to be no outage at all.

### What happened

`remind_me_sync_status` on node `baileyai-connector` reported `drain: stalled`, 57249 pending, 0 sent, and `last_push: 1970-01-01` on every remote — while the hub was reachable and pulls were landing throughout. Every alarm signal was an instrumentation defect. No data was ever at risk.

The cost is real even so. The status surfaces added by SY-12 and SY-14 exist precisely to answer "is sync healthy?", and they currently answer "no" on a healthy node, which trains the reader to ignore them.

- **SY-15** ([#102](https://github.com/baileyrd/remind_me/issues/102)) — `sync_log.last_push` is declared (`db.py:547`) and read (`sync.py:1176`) but written nowhere in the repo, so it is structurally incapable of holding any value but the epoch. It reads as "this node has never once pushed". `ever_contacted` derives from it and is really "ever *pulled*".
- **SY-16** ([#103](https://github.com/baileyrd/remind_me/issues/103)) — the outbox counters measure echo suppression, not push progress. A successful push records its ack in `sync_sends` (`sync.py:200-204`) and never sets `sent_at`; the only writers of `sent_at` are the four echo-suppression paths. So `pending` (`sent_at = ''`) really means "written locally" and `sent` really means "arrived from a remote", and neither moves when a push succeeds. The `drain` sampler reads the same column, making `stalled` the permanent steady state of any healthy node that writes its own memories — from the one signal built specifically to distinguish a healthy backlog from a wedged push.
- **SY-17** ([#104](https://github.com/baileyrd/remind_me/issues/104)) — `last_pull` is a keyset cursor over record `updated_at` (`sync.py:264-284`), not a contact time, but is presented as one. It also updates only when a page contained records, so a pull returning nothing new leaves the row untouched — exactly the pulls that prove a remote is reachable. `_verdict` compares this content watermark against wall-clock and returns `fault` ("the pull is not running") for a healthy quiet remote.
- **SY-18** ([#105](https://github.com/baileyrd/remind_me/issues/105)) — the root cause behind SY-15 and SY-17: `sync_log` has one pair of columns doing two unrelated jobs (resume-cursor and liveness clock) and maintains only the first. The result is that no per-remote record of *when we last successfully communicated* exists anywhere in the system — which is why diagnosis required reading the sync implementation rather than glancing at the status output. Proposes renaming the cursor columns to `pull_cursor_ts`/`pull_cursor_id` and adding true wall-clock `last_pull_at`, `last_push_at`, and `last_attempt_at`.

`last_attempt_at` is the load-bearing addition: with only `last_error` (null in the healthy case), "never attempted", "attempted and succeeded", and "attempted and failed without recording an error" are indistinguishable, and they have different causes and different fixes.

Fix order is SY-18 first — SY-15 and SY-17 collapse into "point the existing reader at the new column" once it lands. SY-16 is independent counter logic.

## v1.21.0 — 2026-07-30

New capability: **`remind_me_undo_import`** — roll back a bulk import.

Imports are the one bulk write this server makes, and there was no bulk way to undo one. `remind_me_delete` takes a single id, which is unusable at import scale: a single mempalace run on a live node accounts for 47000 of 49513 memories (95%) and most of a 212 MB database. Removing that by hand meant either 47000 tool calls or raw SQL — and raw SQL is the trap, because it silently orphans everything derived.

### The tool

- **Targets a specific import, not a category.** Each import path records what it created: `mempalace_imports` and `dbs_imports` store a `memory_id` per row, while `chat_imports` keys on `import_id` which the importer stamps onto `memories.doc_id`. The tool follows those links rather than pattern-matching on `category`, which is only approximately right — category and source counts already disagree on this store (47000 vs 46879 + 118 + 3).
- **Dry run by default.** Reports exactly what would go and changes nothing until `dry_run=false`. Bulk deletion that propagates across every node should be opt-in, not the default path.
- **Scopable.** `import_id` narrows to one chat import, one dbs source, or a mempalace drawer prefix (so a single wing can be undone without naming every drawer). A scope that matches nothing removes nothing — a typo is inert, never a full-store wipe.
- **Resumable and bounded.** `limit` (default 500) caps one call so a large undo cannot exceed the MCP call timeout; callers loop until `remaining` is 0. Re-running after completion is a no-op.
- **Clears the import-tracking rows too.** This is the non-obvious part: import paths skip anything already recorded, so leaving those rows behind would make the same content permanently un-importable. For chat imports the tracking row is per-file, so it is dropped only once none of its chunks survive — a partially-drained import keeps its row and cannot be duplicated by a re-import.
- **Honest about disk.** On a sync-enabled node this is a soft delete: rows are tombstoned so the removal propagates to every other node, which means space is *not* reclaimed until compaction (`TOMBSTONE_RETENTION_DAYS`, default 180). The tool says so rather than implying the database shrinks.

### Refactor: one delete path instead of five

Deletion goes through `db._purge_memory`, extracted in this release. The steps are easy to get subtly wrong — chunk vectors, the ANN index entry, entity mention links, stored feedback, and the tombstone-vs-hard-delete split — and were copy-pasted across four call sites (the MCP delete tool, two dashboard REST routes, and sync's tombstone compaction). They had already drifted: **both REST routes skipped the `memory_feedback` cleanup** that the MCP tool performed, so deleting from the dashboard orphaned feedback rows. Extracting the helper fixes that inconsistency and means the new tool could not become a fifth divergent copy.

`soft` is an explicit argument rather than read from `config.SYNC_ENABLED` inside the helper, so each caller keeps its own patchable flag and the behaviour is visible at the call site.

Tests: 13 new cases covering dry-run inertness, tombstone vs hard delete, derived-row cleanup, batching and resumability, scoping, the un-importable-tracking-row trap, and that a typo'd scope matches nothing. Full suite 1514 passed / 17 skipped, coverage 90.56%, on all four legs.

The v1.20.0 entry stated that `v1.1.0` was the repository's only tag and that 59 commits had landed since. Both were wrong, and the correction is marked inline there rather than silently rewritten.

There are **six** tags: `v1.0` and `v1.1` (2026-02-24), `v1.2` (2026-03-05), `v1.1.0` (2026-07-20), and `v1.20.0` / `v1.21.0` (2026-07-30). The real gap from `v1.1.0` was 62 commits.

## v1.19.5 — 2026-07-30

Completes the sync observability set begun in v1.19.4. SY-12 answered "is my local sync healthy?" and SY-13 made the hub's counts readable; this closes the loop with "does my data actually match the hub?"

### New Features

- **`remind_me_sync_reconcile` (SY-14)** — fetches the hub's `GET /stats`, diffs it against local counts, and returns per-category drift with a **verdict**. Read-only on both sides. Replaces a manual exercise: `psql` on the hub host, local counts gathered separately, two tables diffed by eye.
  - Verdicts are `in-sync`, `pull-lag`, `node-ahead`, and `fault`. The judgment is the deliverable — the benign case and the real fault differ only by a *sign*, which is easy to skim past when reading two count tables. `node-ahead` (local > hub) is checked first and outranks everything, because it's the only direction meaning this node holds records nothing else has.

Instead, hub-ahead drift keys off *pull freshness*: a recent successful pull means ordinary lag; a stale one (beyond `max(3 × SYNC_INTERVAL, 300s)`) or none at all means the pull isn't running. Identical numbers, different verdict, decided on real evidence.
  - Local counts deliberately **do not** filter `deleted_at IS NULL`. The hub counts every row and reports tombstones separately, so filtering locally would make a healthy node look permanently behind by exactly its own tombstone count — a false `pull-lag` that never resolves.
  - Categories are compared as a **union** of both sides, so a bulk import that never reached the hub shows up rather than being silently intersected away. Only drifting categories are listed; agreement is reported as a count.
  - Degrades with a named cause instead of a stack trace: `unsupported` when the hub predates SY-13 and 404s `/stats` (the state a rolling upgrade passes through, node-first), `unauthorized` on a `SYNC_SECRET` mismatch, `unreachable` on connection failure, and `disabled` without contacting the hub at all.

Tests: 15 new cases covering every verdict and failure mode, including that `node-ahead` outranks a healthy pull (a node can pull fine while its pushes fail), that tombstones don't read as drift, and that a malformed hub payload yields zeros rather than raising. Full suite 1484 passed / 12 skipped, coverage 90.27%.

Verified against the real 2026-07-29 hub-vs-node numbers: correctly returns `pull-lag` with the same three drifting categories (`dialog` +10, `conversation` +6, `homelab` +2) and 5 categories in sync that a manual reconciliation found.

### New Features

## v1.8.0 — 2026-07-21

Closes a precision gap flagged in the application capability review: `rank_rrf` fuses keyword, semantic, recency, vitality, and IDF signals purely by ordinal rank position, discarding the actual score magnitude — a 0.95-cosine semantic match and a 0.55-cosine match tie if they happen to land in adjacent rank positions, even though one is a far stronger match than the other.

### New Features

- **Score-based fusion mode, opt-in** — `rank_rrf` gains a `fusion` parameter (`"rank"` default, `"score"` new) plus a module-level `REMIND_ME_RRF_FUSION` env var. `"score"` mode min-max normalizes the real underlying magnitudes across the candidate pool — FTS5 `bm25()` score, semantic distance, `created_at`, and `vitality` — into `[0, 1]` (higher = better) and sums `weight * normalized_score`, instead of `1/(k + rank)` terms. A memory missing a signal (e.g. a semantic-only hit has no `bm25` score) gets `0.0` for that signal, mirroring rank mode's penalty-rank treatment. `w_idf` reuses the same normalized keyword score in this mode, since both derive from the identical `bm25` magnitude. `"rank"` stays the default, so existing callers and benchmark numbers are unaffected unless explicitly opted in.
- Rank fields (`_keyword_rank` etc.) are still computed and set in `"score"` mode too, so existing debug tooling keeps working; `build_debug_signals` additionally surfaces `keyword_score`/`semantic_score`/`recency_score`/`vitality_score`/`fusion_mode` when score fusion was used (omitted entirely for rank-mode results).
- `benchmarks/runner.py` gains `--rrf-fusion {rank,score}`; `benchmarks/before_after.py` gains `--compare score_fusion` for A/B measurement against the rank-only baseline.

## v1.7.0 — 2026-07-21

Ships the single most-cited unused retrieval-quality lever flagged in the application capability review: cross-encoder reranking (`reranker.py`) was built, tested, and off by default — adoption was effectively zero even though `benchmarks/RESULTS.md` already documented its value clearly.

### Improvements

- **Reranking on by default** — `REMIND_ME_RERANK` now defaults to `"onnx"` instead of unset. Rescoring only ever touches the bounded `REMIND_ME_RERANK_TOP_K` (default 20) head of the RRF-ranked list regardless of how large the underlying result pool is, so the added latency is small and constant. Set `REMIND_ME_RERANK=""` to opt back out for latency-sensitive deployments.
- **Stronger default cross-encoder** — `REMIND_ME_RERANK_MODEL` swaps from the 2019 `cross-encoder/ms-marco-MiniLM-L6-v2` to `BAAI/bge-reranker-base` (2023), still small enough to run on CPU but meaningfully stronger. Fully overridable via `REMIND_ME_RERANK_MODEL` regardless.
- **Reranker failure caching (PF-01)** — `CrossEncoderReranker` now caches load failures exactly like the embedder already does: a missing dependency is permanent for the process, and any other failure (no network, no ONNX export for the configured model) is retried only after a cooldown instead of re-attempting a live HuggingFace download on every single search — necessary now that reranking runs for everyone by default, not just users who explicitly opted in.
- `benchmarks/runner.py`'s `--rerank` flag now explicitly forces the backend on or off, so lever-isolation benchmark runs stay correct regardless of the library's own default.

## v1.6.0 — 2026-07-21

Closes a retrieval-quality gap: modern embedding models (`nomic-embed-text`, `bge-*`, `e5-*`) are trained with an asymmetric query/passage convention — a search query and an indexed document are expected to carry different instruction prefixes (e.g. `search_query:` vs `search_document:`). remind_me embedded both identically, silently leaving quality on the table for anyone using one of these models via the Ollama backend.

### Improvements

- **Query/document embedding prefix asymmetry** — `_Embedder.embed`/`embed_one` (ONNX) and `OllamaEmbedder.embed`/`embed_one` gain a `role: Literal["query", "passage"]` parameter (default `"passage"`). A per-model-family lookup table (`embeddings._ROLE_PREFIXES`, matched by substring against the configured model name) applies the correct instruction prefix — `nomic-embed-text`'s `search_query:`/`search_document:`, `e5-*`'s `query:`/`passage:`, `bge-*`'s query-only instruction — before encoding. Models with no known convention (the ONNX default `all-MiniLM-L6-v2`) are unaffected — no prefix, identical behavior to before.
- Every embed call site is now correctly labeled: document chunks are embedded with `role="passage"` at write time; a search query is embedded with `role="query"`; a fused query+HyDE-passage embedding embeds the literal query as `"query"` and the synthetic HyDE passage as `"passage"` before averaging, rather than treating both halves as the same role.

## v1.5.0 — 2026-07-21

Closes a real gap in the living-memory model: supersession only ever happened via similarity-merge (near-duplicate memories get consolidated), so a genuinely contradictory update — "I moved to Boston" — never replaced an old fact like "I live in Seattle," since the two statements share no text.

### New Features

- **Contradiction-based supersession** — a new `_supersede_contradicting_facts` (`db.py`) deterministically supersedes any other non-superseded, non-deleted memory that shares a new/updated SPO triple's subject+predicate but has a different object. Wired into every place a triple gets attached to a memory: `remind_me_add`, `remind_me_decompose` (per extracted fact), and `remind_me_annotate` (re-checking the memory's full current triple, since annotations can be partial). Uses the same `superseded_by` mechanism as similarity-merge, so every existing superseded-exclusion read path (search, list, entity lookups) picks it up automatically.
- Deliberately narrow to avoid false positives: a differently-worded predicate never contradicts — "I live in Seattle" and "I visited Boston" don't collide, since they don't share a predicate.

## v1.4.0 — 2026-07-21

Fixes a real multi-device correctness bug: sync had no delete semantics at all. Deleting a memory on one device was a hard `DELETE`, which produces no `sync_outbox` row (the sync triggers only fire on INSERT/UPDATE) — so the next pull from another device silently resurrected it.

### New Features

- **Delete/tombstone propagation across sync** — a new `deleted_at` column turns delete into a soft-delete UPDATE, which rides the *existing* update-outbox trigger and last-write-wins conflict resolution for free — no new operation type or wire format. Every normal read path (search, list, get, entity profile, dashboard REST routes) excludes tombstoned memories; sync's pull/push wire paths and full-backup exports deliberately don't, since they need to carry/preserve tombstones.
- **Automatic tombstone compaction** — a background pass hard-deletes tombstones older than `REMIND_ME_TOMBSTONE_RETENTION_DAYS` (default 180, deliberately more generous than the 30-day outbox retention) so the table doesn't grow forever.
- **Hub parity** — the Postgres hub's schema, upsert, and pull-wire columns all carry `deleted_at`, so hub-mediated sync propagates tombstones exactly like direct peer sync.
- On a node with sync disabled entirely, delete stays a plain, immediate hard delete exactly as before — there's nothing to propagate to, so nothing changes for single-device users.

## v1.3.1 — 2026-07-21

Defense-in-depth fix, not a new capability: the sync pull path was the one caller of `_embed_and_store_rows` that never batched its input, relying entirely on the downstream `EMBED_FORWARD_BATCH` forward-pass cap (added in PR #15) to bound memory.

### Improvements

- **`_embed_and_store_rows` now batches internally** by `EMBED_BATCH_SIZE`, regardless of how many rows a caller passes in one call — a single source of truth for "no caller flattens the whole store into one embed()/transaction," instead of every bulk caller having to remember to pre-slice its own input. Fixes sync's pulled-record embedding (`_upsert_records`) without any change to `sync.py` itself.
- Removed the now-redundant external batching loops in the file/mempalace/dbs importers — each now hands its rows to `_embed_and_store_rows` in one call, same as sync already did.

## v1.3.0 — 2026-07-21

Semantic search's `sqlite-vec` KNN was an exact brute-force scan over every chunk vector — correct, but O(n) per query, the one thing that would visibly degrade as a memory store grows into the tens of thousands of chunks.

### New Features

- **Optional ANN index for semantic search** — a new `ann_index.py` module adds an HNSW approximate-nearest-neighbor index (via the `usearch` package, new `ann` extra) that `_semantic_search` consults once a store passes `REMIND_ME_ANN_MIN_CHUNKS` chunk vectors (default 5000, opt-in-by-scale). Below that threshold, or if `usearch` isn't installed, or if the ANN path itself fails for any reason, search transparently falls back to the existing exact brute-force scan — same output shape, same `semantic_distance` meaning either way.
- The index is self-healing: held in memory for the life of the process, mutated incrementally as chunks are added/removed, persisted to disk on clean shutdown, and automatically rebuilt from `memories_vec` if the on-disk index is missing, corrupt, or size-mismatched (e.g. after a hard crash).
- `remind_me_server_status` reports ANN index state (built, vector count, threshold) alongside the existing semantic-search status.
- Benchmarked at 20k chunk vectors: ~11x faster than the brute-force scan, identical top result.
