# Changelog

All notable changes to this repo are documented here.
Format: Added / Changed / Deprecated / Removed / Fixed / Security, newest first.

## [Unreleased]
### Added
- **A `reference` memory_type for standing reference material (#220).** The other seven types all describe a *claim*; bulk-imported file contents — source code, SVG diagrams, doc fragments — assert nothing, and were being filed as `fact` for want of anywhere better, which made `fact`-filtered views a mixture of real assertions and pasted-in source. Named `reference` rather than `source_snippet` because the content is not only code, and a name that says "code" would push the next importer of non-code reference material straight back into `fact`. `DECAY_RATES["reference"] = 0.03` — below `fact`'s 0.05, since time alone does not stale a snippet the way it stales a claim about current state, but above `decision`'s 0.02, since the file a reference mirrors changes more often than a decision is reversed. `BASE_WEIGHT_TYPE_PRIORS["reference"] = 0.95`, slightly below neutral because it arrives in bulk and is something you look up deliberately rather than something that should crowd a decision out of an unprompted recall.
- Schema v28 → v29 refiles existing memory-palace imports from `fact` to `reference`. Deliberately narrow — only rows whose `source` marks them as such — because a broader "looks like code" heuristic would be guessing at content the user classified on purpose. It moves `decay_rate` with the type (stored per row, so the type would otherwise be cosmetic) and `updated_at` too, so a node that upgrades later cannot push its stale `fact` back over an upgraded node's `reference` under last-write-wins.
- Hub: `HUB_VERSION`, reported by `GET /health` (unauthenticated), `GET /count` and `GET /stats`.
- Hub: `GET /count` — bearer-authenticated scalar record counts with no `GROUP BY`, optionally narrowed with `?table=`; `memories` splits `live` from `tombstones`.
- MCP: the installed package version is reported by the dashboard's `GET /health`, the peer server's `GET /health`, `remind_me_sync_status`, and `remind_me_sync_reconcile` (which also reports `hub_version`).
- Hub: `GET /metrics` (Prometheus, bearer-gated, `REMIND_ME_HUB_METRICS_ENABLED`), `X-Hub-Version` on every response, `?approx=1` planner-estimate counts, and `?since=`/`?by=origin_node` filters on `/count`.
- Hub: OCI image labels and version-tagged images, so a stopped container can be identified and a rollback is a retag.
- MCP: `remind_me_build_info{version=...}` metric; version in `remind_me_server_status` and `--status`; version shown in the dashboard header.
- MCP: `GET /count` on the peer server and a `remind_me_sync_reconcile_peer` tool, so peer drift is observable; `remind_me_sync_reconcile` gains an opt-in `quick` pre-check.
- CI: `hub-e2e` job runs `hub/e2e_test.py` against a live Postgres — the hub's first automatic runtime coverage — plus a guard requiring a `HUB_VERSION` bump when `hub/main.py` changes.
- MCP: `GET /api/versions` — this node's build and, when sync is configured, the hub's (probed live, `null` when unreachable); the dashboard header shows both.
### Changed
- MCP: `__version__` now resolves in `remind_me_mcp/version.py` so HTTP surfaces can import it without cycling through the package root; `from remind_me_mcp import __version__` still works.
### Fixed
- **`remind_me_contradiction_candidates` can now page past the first result (#219).** The query ordered by `(id_a, id_b)` but took no cursor, so every call returned byte-identical results — on a vault with ~78k candidate pairs, 100 were reachable and the other 77,900+ were not, and a worker looping the tool made no progress at all. It now accepts an `(after_a, after_b)` keyset cursor and returns `next_after_a`/`next_after_b`/`has_more` to drive it. A keyset rather than an offset because the pair set is derived from live memories: an edit between calls shifts an offset's window, silently skipping or repeating rows. Of the three approaches the issue floated, this is the only one that keeps the module read-only — excluding already-reviewed pairs needs somewhere to record a review, and ordering by `updated_at` fails outright since most pairs are correctly judged *not* to conflict, so reviewing them changes nothing and they would be re-served forever. Passing half a cursor is rejected rather than silently paging from the wrong place. `total_candidates` still describes the whole queue, not the remainder after the cursor.
- **Sync: the client now uses the hub's `since_seq` pull cursor (#167), so #160's fix finally works end to end.** #160 gave the hub a monotonic `hub_seq` and an opt-in `since_seq` cursor, but nothing consumed it — `sync.py` still tracked only `(updated_at, id)`, so the bug it was filed for stayed live: a node back online after a fortnight pushes records still stamped with old timestamps, which sort *behind* every other node's already-advanced cursor and are permanently invisible to them. `_pull_remote` now probes each remote once (`since_seq=0&limit=1`, checking whether the returned record carries a `hub_seq` — a 200 alone proves nothing, since an older hub ignores the unknown parameter) and then pulls by sequence. Peers, whose SQLite store has no sequence, are recorded as unsupported and stay on the legacy cursor; `remind_me_sync_repair` clears that verdict, which is the documented path after upgrading a hub. New `sync_log.last_pull_seq` column (schema v27 → v28). Establishing the cursor starts at `0` — a deliberate one-time full re-walk, because the records this rescues are exactly the ones a legacy cursor has never returned, so no watermark derived from legacy pulls can be trusted to sit below them; the re-walk is bounded per cycle and almost entirely no-ops, since a record matching the local copy loses last-write-wins and is neither rewritten nor re-embedded.
- **Hub: the legacy-schema migration corrupted sub-second timestamps, and with them the pull cursor and LWW.** Converting a restored legacy dump's `TIMESTAMPTZ` columns to canonical TEXT stripped *all* trailing fractional zeros, so `.500000` became `.5` — a value `datetime.isoformat()` never produces, despite the code's own comment saying the goal was to match it exactly. Under `COLLATE "C"` that sorts **before** the client's own `.500000` (`+` is 0x2B, `0` is 0x30), so a migrated row compared as *older* than the identical instant on the node that wrote it: the keyset pull cursor could skip it permanently, and last-write-wins could resolve the wrong way. It affected any legacy row whose microseconds were non-zero and ended in a zero — roughly one in ten. Now only a wholly-zero fraction is stripped. Covered by a new `hub/e2e_test.py` section that executes the live expression against a real Postgres (the migration had no test at all before this), plus a static guard in `tests/test_hub_fixes.py`. Found while porting the hub to Rust in `rusty_remind_me`.
- **`_ensure_schema` no longer requires `row_factory = sqlite3.Row`.** The v27 → v28 migration read a `PRAGMA table_info` row by name, the only place in `db.py` to do so, while `_ensure_schema`'s own contract asks for nothing more than "an open SQLite connection" — the query helpers that *do* need `sqlite3.Row` say so explicitly. Calling it on a bare connection raised `TypeError: tuple indices must be integers or slices, not str`. The whole test suite was blind to it because every caller sets the row factory a line before calling in, so 2176 tests passed over the break; it surfaced from `rusty_remind_me`'s ADR-0007 schema regeneration, which imports `db.py` standalone and is the one documented consumer that does not set a factory. Now indexed positionally, which reads the same through a tuple or a `Row`, and guarded by a test that builds its connection by hand rather than from a fixture — a fixture is what hid this.
- Hub: `setup.sh update` reported success without checking that the new build was actually serving.
- Hub e2e: two assertions expected exactly one entity, unsatisfiable since entity relations were added.
- `docs/openapi.yaml` drift for `/api/versions`, and an order-dependent test that patched a shared `httpx` global and left module-level cache state behind.
